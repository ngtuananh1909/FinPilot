# 14 · SQL review of the candidate migration (T01.3)

Scope: `supabase/migrations/202611230001_finpilot_initial.sql` (candidate, **never applied**, treated as immutable).
Output: draft `supabase/proposed/202611230002_finpilot_hardening.sql` (+ `.rollback.sql`), tests in `tests/db/`, and the G2 request in `docs/15-g2-migration-approval-pack.md`.

**Status of evidence.** Nothing here was applied to or checked against the hosted Supabase project. Two kinds of evidence exist:
- *Static*: Vitest tests parse the SQL text (`tests/db/sql-static.test.ts`).
- *Local smoke (not a Supabase test)*: during review the base and proposed SQL were run once in a throwaway local `postgres:16` container with hand-written stubs for the `auth` schema and the `anon`/`authenticated`/`service_role` roles, then the container was removed. This confirms syntax, idempotent re-run (second apply: no errors), rollback execution, and the behaviours marked "local PG16" below. It does **not** prove behaviour on Supabase (different default ACLs, GoTrue-managed `auth.users`, PostgREST, real JWT roles). The live suite in `tests/db/rls.live.test.ts` remains **BLOCKED** until G2.

## Findings

| ID | Severity | Issue | Fix (in proposed migration unless noted) |

| F01 | Medium | `updated_at` exists on 5 tables (`financial_profiles`, `recurring_items`, `transactions`, `savings_goals`, `ai_conversations`) but nothing maintains it; it stays at insert time and clients can write any value. | `public.set_updated_at()` (`set search_path = ''`) plus a `before update` trigger per table. Forces `now()`, so it cannot be forged. Local PG16: an update that set `updated_at = '2000-01-01'` ended with the current time. |
| F02 | **High (bug)** | `transactions_owner_recurring_fk` is `on delete set null (recurring_item_id)`. That nulls only `recurring_item_id`; `recurring_instance_date` stays set and violates `recurring_instance_pair_check`. Deleting a referenced recurring item therefore fails with a confusing check error. Deleting an `auth.users` row may fail too, depending on the order in which the two cascades (to `recurring_items` and to `transactions`) run. Local PG16 reproduced the first failure; the ordering failure was not reproduced and is theoretical. | Re-add the constraint as `on delete no action` (checked at end of statement). **NO ACTION, not RESTRICT**: RESTRICT is checked immediately and could block the user-delete cascade. App rule: recurring items are **deactivated** (`active = false`), never deleted, once any transaction references them. Local PG16: deleting a referenced item is rejected (`23503`), deactivation works. The drop/re-add touches only this one constraint and is skipped when it is already `NO ACTION`. Rollback restores the original (defective) definition. |

| F04 | High | Anonymous guests are role `authenticated`, so any privileged function not explicitly revoked from `authenticated` is callable by every guest. Ownership: functions are owned by the migration role (`postgres`), which bypasses RLS on its own tables; that is intended, so callers must verify the session and pass the verified `p_user_id`. The migration does not `alter function ... owner`. `FORCE ROW LEVEL SECURITY` is not used. Check the owner read-only before G2 (see docs/15). |
| F05 | Medium | The base file grants specific privileges to `authenticated` but never revokes what Supabase default privileges may already have granted. Default ACLs can include `TRUNCATE`, `REFERENCES`, `TRIGGER` (RLS does not cover TRUNCATE) and write privileges on the AI tables, and may grant everything to `anon`. RLS currently stops row access, so this is defence in depth. | Revoke all table privileges from `anon`; revoke `truncate, references, trigger` from `authenticated` on the five client-writable tables; revoke `insert, update, delete, truncate, references, trigger` from `authenticated` on `ai_conversations`, `ai_messages`, `ai_proposals`, `ai_usage_daily`. Local PG16 (with an over-granting default ACL stub): `truncate public.transactions` and inserts into `ai_usage_daily` as `authenticated` were denied. The rollback does not re-grant. |
| F06 | Medium (bug) | `consume_ai_quota`: `p_kind not in (...)` and `p_limit <= 0` evaluate to NULL when the argument is NULL, so the guard does not raise. A NULL kind inserts a 0/0 row and returns **true** (granted, nothing counted). Local PG16 reproduced `consume_ai_quota(uuid, null, 5)` returning `t`. Service-role only, so low exposure, but it is a quota bypass. The rest of the function (row-locked upsert with the `where` limit) is atomic and correct. | Redefined with explicit `is null` checks; logic otherwise unchanged. Signature and grants unchanged. Local PG16: the new version raises. New server code should use `reserve_ai_quota` instead (F07). Do not mix both for one request. |
| F07 | Medium | The approved quota policy needs release on pre-result failure and at most one reservation per request id. `consume_ai_quota` has no request identity, so a release would be a blind decrement that can double-refund. | `ai_quota_reservations` plus `reserve_ai_quota`, `release_ai_quota`, `commit_ai_quota`. Reserve takes an advisory lock on the request id, replays are idempotent, another owner's id raises, a released id returns false (retry needs a new id). Release is one `UPDATE ... WHERE status = 'reserved' AND user_id = p_user_id`, so only the first call decrements, and it decrements the reservation's own `usage_date`, not today's. The 50-way **concurrent** test exists only in the blocked live suite. Policy text: release on clear pre-result failure (invalid configuration, definitive provider rejection); keep the reservation on ambiguous timeout; commit when a usable result is delivered. Reservations accumulate; cleanup is not authorised by any document. |

### F14 · Guest and anonymous notes
- Anonymous users have role `authenticated`; no policy uses `to anon`. Static tests assert no grant to `anon`/`public` in the proposed file.
- Quotas are per user id. A guest can create a new anonymous identity and receive a new 20/5 allowance. The approved policy has no schema-level answer; it needs the IP/abuse limits already named in `docs/08` item 5, and Supabase anonymous sign-in rate limits. Not solvable in SQL.
- `reset_user_to_persona` is generic: it resets whichever `p_user_id` it receives. Two documents differ on whether the 3 sample email accounts may be reset (`supabase/README.md`: guest reset never resets them; `docs/08`: optional manual reset per account). The route handler must enforce the chosen rule. **Open question for the owner.**
- Reset deletes chat history and pending proposals because they describe the replaced data. It never touches `ai_usage_daily` or reservations, so reset cannot refill quota.
- Guest TTL cleanup is not authorised (`docs/08`). With the F02 fix, a future user-scoped deletion by id cascades cleanly.
- Linking an anonymous user to an email keeps the same uid, so RLS data stays attached.

## Migration 0003 (PROPOSED, not applied)

Draft: `supabase/proposed/202611230003_finpilot_profile_protection_and_csv_commit.sql` (+ `_rollback.sql`). Approval request: `docs/18-g2-approval-pack-0003.md`. Migrations 0001 and 0002 are applied and immutable; 0003 only adds objects (no DROP, TRUNCATE, UPDATE or DELETE statement, no RLS, policy or table-grant change).

| ID | Severity | Issue | Fix |
|---|---|---|---|
| F15 | Medium | RLS limits rows, not columns. An `authenticated` client (every anonymous guest included) can PATCH its own `financial_profiles` row through PostgREST and change `persona_code` and `is_demo`. `is_demo` is a safety flag (the demo reset path refuses real accounts), so a guest can downgrade or forge it. `user_id` is protected only by the RLS `WITH CHECK`. | `public.protect_profile_columns()` (SECURITY INVOKER, `set search_path = ''`), attached as `BEFORE INSERT` and `BEFORE UPDATE` row triggers. When `current_user in ('authenticated','anon')`: an UPDATE that changes `user_id`, `persona_code` or `is_demo` raises `42501`; an INSERT must have `persona_code is null` and `is_demo = false`. |
| F16 | Medium | CSV commit is two calls from the route (insert `import_batches`, then bulk insert `transactions`, then a third call to mark the batch failed). A crash between calls leaves a committed batch with no rows, and the failure marker itself can fail. | `public.commit_csv_import(p_user_id, p_idempotency_key, p_filename, p_rows jsonb, p_rejected_count)`: one transaction, SECURITY DEFINER, `service_role` only. |

### Design decisions
- **`current_user`, not `session_user`.** PostgREST connects as `authenticator` and runs `set local role authenticated`, so `current_user` is the client role and `session_user` stays `authenticator`.
- **Trigger instead of column grants.** The base grant is table-level, and a column `REVOKE` does not remove a table-level privilege, so column grants would mean revoking `UPDATE` on the table and maintaining an allow-list on every new column. They also reject upserts and full-row echoes that leave the protected columns unchanged, and cannot express "insert only with persona null and `is_demo` false". The trigger compares OLD with NEW, so an unchanged value is accepted and only a real change is rejected.
- **Server paths keep working.** `service_role` has `current_user = 'service_role'`. `bootstrap_profile` and `reset_user_to_persona` are SECURITY DEFINER, so inside them `current_user` is the function owner. Local PG16 confirmed both (including a persona insert and an `is_demo = true` upsert).
- **`balance_snapshot_vnd` / `balance_snapshot_at` stay client-editable.** They are the user's declared starting balance (Settings), cannot cross an owner boundary, and the engine treats them as user input.
- **Residual.** A client can still DELETE its own profile row and insert a plain one (persona null, `is_demo` false). That only changes its own demo state; the server restores it with `bootstrap_profile`. Revoking client DELETE on `financial_profiles` is a possible follow-up, not part of 0003.
- **Same advisory lock as reset.** `commit_csv_import` locks `hashtextextended(p_user_id::text, 0)`, the key `reset_user_to_persona` uses, so an import and a reset of one user are serialised.
- **Replay before validation.** A repeated `(user, key)` returns the stored batch (`replayed: true`) without re-validating or inserting; a different payload under a used key still returns the original result (same as today's service). A key stored by a `receipt` batch is refused.
- **Validation.** 1..5000 rows; only the keys `occurred_at`, `kind`, `amount_vnd`, `category`, `merchant`, `description`, `fingerprint` (a row cannot carry `user_id`, `source` or `import_batch_id`); `kind` in income/expense/excluded; amount 1..9007199254740991 through `parse_safe_vnd`; category (blank becomes `other`) <= 50, merchant <= 200, description <= 500, fingerprint non-blank <= 128, key <= 128, filename <= 255, rejected count 0..5000; `occurred_at` ISO with offset. An impossible calendar value that passes the format check (month 13) raises `22008` from the cast and rolls back; it is still all-or-nothing. The merchant/description caps mirror the TypeScript schema; the tables have no such check. The TypeScript category pattern is not repeated in SQL.
- **How the route will call it (not wired).** After `auth.getUser()` and quota/authorisation checks, the route re-parses and re-classifies the CSV on the server as today, then calls `commitCsvImportRpc(serviceClient, owner, { idempotencyKey, filename, rows, rejectedCount })` from `src/lib/db/repositories/server-only/csv-commit.ts`. The wrapper sends `p_user_id = owner.userId` and amounts as decimal strings. It is not exported from the server-only barrel and `src/lib/import/service.ts` does not use it. Until 0003 is applied it fails with `rpc_unavailable`.

### Local smoke test (throwaway `postgres:16` container, `--network none`, stubbed `auth` schema and roles; container removed afterwards)
Base, 0002 and 0003 applied; 0003 applied a second time without error; rollback run twice (second run only NOTICEs), re-applied. Results:
- As `authenticated`: UPDATE of `persona_code` (to another value and to null), `is_demo` and `user_id` raised `42501`; `minimum_reserve_vnd`, `balance_snapshot_vnd`, `display_name` and an echo of unchanged protected values were accepted; `INSERT ... ON CONFLICT DO UPDATE` with unprotected columns worked; INSERT with `is_demo = true` or a `persona_code` (plain, and in `ON CONFLICT DO NOTHING`) raised `42501`; a plain INSERT worked.
- `service_role` UPDATE of both columns worked; `bootstrap_profile` with a persona and `reset_user_to_persona` (sets `is_demo = true`) worked.
- `commit_csv_import` as `service_role`: 3 rows committed with source `csv`, batch id and fingerprint; blank category became `other`; the replay returned `replayed: true` and inserted nothing; 14 invalid calls (zero amount, amount 2^53, unknown key `user_id`, bad date format, bad kind, non-string merchant, fractional amount, empty array, non-array, month 13, null user, unknown user, 5001 rows) left 0 batches and 0 transactions; 5000 rows committed; `anon` and `authenticated` got `42501`.
- 50 concurrent same-key calls (50 `psql` sessions, 200 rows each): one `replayed: false`, 49 `true`, 1 batch, 200 transactions.
- Rollback removed both triggers and both functions and left all rows in place.
